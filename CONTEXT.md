## Current state (v1.1)
Single-owner mode works (v1) plus the first product layers (v1.1):

- **Web app** (`web/`, vanilla ES modules, no build, GitHub Pages): Home (film-strip of today's slots), Pages & channels (v1.1: colour chips, progress, bulk select/pause/posts-a-day/time-window), Flows, Videos, Accounts, Schedule, Stats, Activity, Settings, Help, Setup. Ctrl/Cmd+K or "/" command palette (v1.1). Skeleton loading (v1.1). PWA. Light/dark, text size.
- **License service** (`license/`, Cloudflare Worker, free tier; v1.1): see Licensing below. `web/js/license.js`, `v_paywall.js`, `web/app-config.js`.
- **Data** lives in a private repo (`config.json`, `secrets.enc.json`, `ledger.json`, `queues/`, `status.json`, `license.json`, `inbox/*.json`, `logs/`). The UI uses a fine-grained PAT stored in the browser as login; no backend in single-owner mode.

## Data model (unchanged)
`connections[]` {id, kind instagram|google|cloudinary|telegram|ytnet, label, ig_user_id}. `routes[]` = "Flows": source {drive|youtube|instagram|upload}, target {instagram|youtube}, schedule {per_day<=100,start,end,jitter,max_per_run,gap_seconds>=60 for IG}, caption {mode,text,template,hashtag_sets,variants,table}, edit {filter,strength,fit keep|blur|crop|pad,audio,watermark,cover}, order, youtube opts. Ledger entry per post (dedup by source id AND md5 per target; only the "repost" command bypasses). Queue item statuses pending|posted|failed|skipped|missing. Inbox commands: skip, unskip, retry, retry_all, post_now, reorder, caption, repost, rescan, clear_cooldown.

## Hard behaviors (do not regress)
One bad video never stops a queue (3 tries then failed). 3 failures in a row pause a flow 60 min without penalising videos. Account problems (token, rate limit, quota) pause only that account with exponential backoff; mid-run rate limit sleeps 10 min once then retries. Source problems (YouTube blocking datacenter IPs) pause only that flow. Crash recovery via in-flight journal committed before publish; no double posts; Cloudinary files deleted after posting plus sweep. Instagram: graph.instagram.com v21.0, needs public video_url, 100 API posts/24h, token refresh every 20 days. YouTube API uploads about 6/day for new projects. Public repo means unlimited Actions minutes; keep-alive step re-enables the workflow (60-day idle disable).

## Licensing (v1.1)
Goal: no access until paid; each device silently proves itself; no "verify your subscription" step.
1. Browser makes an ECDSA P-256 key (non-extractable, IndexedDB). deviceId = SHA-256 thumbprint of the public key. Registered once.
2. For every call the server issues a one-time nonce (120 s); the device signs `reelio:<purpose>:<nonce>:<deviceId>`. Replays and cross-purpose signatures are rejected.
3. Server returns 402 if unpaid, else a 24 h Ed25519-signed entitlement (claims: st, plan, lim{accounts,posts_month,devices}, exp, wv, cnf=deviceId). `wv` = worker-valid-until (paid period + grace, max 35 days) so 24/7 posting continues while the owner is not opening the app.
4. Checkout (Stripe / Razorpay) carries deviceId in metadata/notes; the signed webhook binds the device to the subscription, so the app unlocks by itself (the paywall polls). States: active, grace (past_due, 3 days), trial (optional), comped (admin), none. Extra devices via one-time link codes with seat limits. Admin routes via Bearer ADMIN_SECRET (grant/revoke/stats).
5. The app pushes the token to `license.json` in the data repo; `worker/reelio/license.py` verifies it offline with `REELIO_LICENSE_PUBKEY` (or `license_pubkey` in config). No key configured = open mode (personal use). Inactive = nothing posts, scan still works, plain message shown. Limits: accounts (first N targets in config order), posts per calendar month.
**Honest limit:** code running on a user's own repo/machine can be patched; this stops casual sharing and makes paying the easy path. Real enforcement needs posting on infrastructure the owner controls (Phase B, multi-tenant).

## YouTube cookie pool (v1.5)
`worker/reelio/cookiepool.py`. The secret `youtube-net.cookies` may hold MANY cookie files (separated by `# ---- next cookie ----` or each starting with the Netscape header; one old-style file still works). Every yt-dlp call (listing, selected videos, clip and long-video downloads) goes through `run_with_pool`: ready cookies least-recently-used first, then one try with no cookie. Errors that are the video's fault (private, removed, disk) never count against a cookie. Health lives in `cookie_health.json` (worker-owned, fingerprints only, never the cookie): blocked rests 30 min / 2 h / 6 h / 24 h and DOES recover; expired (logged out / rotated) rests 6 h / 24 h / 72 h then is parked until replaced. When nothing works the flow's cooldown is the time until the soonest cookie wakes (15 min to 12 h), the fix text says how many cookies were tried, and the existing backup Drive folder path (`engine.fetch_with_backup`) is the final route. `status.json.cookies` carries counts for the app; the app keeps only `cookie_count` in config. UI: `web/js/cookies.js` (Accounts card + flow editor block + one dialog; no "account" is made). Cookies cannot be generated by Reelio (Google blocks unattended logins and it would need the Google password): they come from a logged-in browser. **Cookie Sync add-on** (`tools/cookie-sync/`, MV3 Chrome/Edge): Connect button reads `reelio.token/pass/repo` from the open Reelio tab via activeTab, stores them in `chrome.storage.local`, hourly alarm exports youtube.com+google.com cookies as a Netscape chunk marked `# reelio-profile: <id> <label>`, merges only its own slot into `secrets.enc.json` (`mergeProfile`), updates `config.cookie_count`. Worker identity of a cookie = `p-<id>` when marked (else content hash); content change of a known slot clears its rest timer. GitHub-login mode only (not hosted).

## Reliability layers (v1.7)
GitHub's cron is best-effort (late or skipped runs). Three independent wake-ups, all safe to overlap because `concurrency: reelio` queues runs and the engine posts only slots that are due (passed slots minus posted today, so a late run catches up the same day): (1) `keepalive/` Cloudflare Worker (cron every 5 min for tick.yml, minute 7 hourly for long.yml; skips when a run is queued/working or started <4.5 min ago; re-enables a disabled workflow); (2) `.github/workflows/watchdog.yml` (starts tick.yml if the last run is 12+ min old); (3) `web/js/heal.js` (app open and status.json older than 15 min: dispatch once per 10 min). Not covered: slots of a previous day are not made up after midnight. Long tab (`v_long.js`) now lists `long-inbox/` and the latest long.yml run so a new request is visible instantly. Not tested live: Worker deployment, dispatch from Cloudflare, watchdog on GitHub.

## Parallel + always-on engine (v1.8)
`Engine._run_routes`: routes are grouped by target account (`route.target.conn`); each group is one thread (max 16), flows inside a group run in order. `Store` methods are wrapped in one RLock (bottom of store.py) and `Engine._lk` guards counters/alerts. `live.py` (enabled by env `REELIO_LIVE=1`, set by tick.yml when action is `run`): loop of `Engine(..., live=True)` passes; live mode posts max 1 per route per pass, skips a route while the account's `last_post_at` is younger than gap (5 s if the item is Post now), never sleeps for rate limits (cooldown backoff handles it), sweeps Cloudinary at most every 10 min, skips writing status when nothing happened (<120 s). Between idle passes: sleep 15 s + `store.refresh()` (git pull) so app commands arrive. Run ends with ~8 min left, writes `more=true`, workflow dispatches the next run. Set config `parallel: false` to go back to one-by-one. Not tested live: real GitHub run length/handover, Instagram behaviour under many simultaneous accounts, git push contention. Stats page: selector (all / account / flow) in `v_more.js`; views/likes exist only for Instagram.
